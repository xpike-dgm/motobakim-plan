# DEBATE-006 — FINAL TIEBREAK REVIEW — FLUTTER VS RN + EXPO

Status: `INDEPENDENT ADVERSARIAL REVIEW / DOCUMENTARY / NO-CODE / TIE UNRESOLVED / FRAMEWORK HELD`
Date: 2026-09-18
Decision level: Phase-4 comparison evidence only; not a framework recommendation, ADR, implementation, provider approval or Gate 4 -> 5 transition

## 1. Bottom line

The Flutter versus React Native + Expo tie cannot be broken responsibly from the current
evidence. No defensible conditional winner is established.

Both finalist records are well-formed closure plans, but both remain `HELD`: neither has a
candidate-specific dependency graph, generated/native diff, clean rebuild, signed artifact,
real-device or assistive-technology result, hosted/local recovery drill, current provider
quote, or owner-approved cost path. A plan that names the evidence to collect is not the
evidence itself.

The result is therefore:

| Candidate | Adversarial disposition | Meaning |
|---|---|---|
| Flutter | `HELD — no candidate-specific closure pass` | The plugin/channel/runner and Dart/native graph is described, not closed. |
| React Native + Expo development builds | `HELD — no candidate-specific closure pass` | The package/config-plugin/prebuild/generated-native graph is described, not closed. |
| Flutter vs RN + Expo | `TIE NOT BREAKABLE FROM CURRENT EVIDENCE` | No material candidate-attributable delta has been demonstrated under the equal event envelope. |

This does not reject either framework. Android-first remains the approved working direction,
and iOS remains a later evidence-gated release. It does not authorize code, a prototype,
purchase, provider, OTA channel, signing arrangement, ADR or Gate 4 -> 5 transition.

## 4. Equal candidate comparison

### 4.1 Dependency, native and generated closure

**Flutter record.** The Flutter closure exercise requires a pinned Flutter/Dart ref and
digest, `pubspec`/`pubspec.lock`, direct and transitive package provenance, plugin
implementations, generated Dart package configuration, generated Android/iOS registrants,
platform-channel glue, Runner/project integration, manifests, entitlements and the actual
Swift Package Manager or CocoaPods path. It correctly states that a plugin package edit is
not necessarily Dart-only and that a generated output must be tied to a reproducible input.

The record intentionally selects no photo package and provides no implementation lock,
native graph, generated diff or artifact. The Flutter 3.47.2/Dart 3.13.2 values are a frozen
comparison snapshot, not proof that a Kavriva repository or release can be reproduced.

**RN + Expo record.** The RN/Expo closure exercise requires a package-manager lock plus
Android Gradle/Maven and iOS CocoaPods/SwiftPM sub-locks, an Expo/RN/React/toolchain lock,
effective dynamic app-config snapshot, complete config-plugin inventory, prebuild/CNG
generation inputs and diffs, autolinking/module metadata, manifests, entitlements and
native module/code-generation boundaries. It correctly states that a native-capable
package or app-config change requires a new development build and that generated output
cannot be the only hidden source of a change.

The record intentionally selects no photo package or plugin and provides no implementation
lock, native graph, generated diff or artifact. Its SDK 57/RN 0.86.3 values are a dated
comparison snapshot, not proof that a Kavriva repository or release can be reproduced.

**Adversarial determination.** Both boundaries are explicit enough to define future work,
but neither is closed. RN + Expo has additional dynamic-config, config-plugin, prebuild and
generated-project surfaces; Flutter has plugin/channel, generated registrant, Runner and
host package-manager surfaces. This is a structural observation, not a measured maintenance
or failure result. Without the exact dependency and generator event, it cannot become a
winner claim. Both remain `HELD` on the same critical closure question: can every changed
input and every generated/native output be regenerated, exported and independently verified?

### 4.2 Optional-photo replacement or retirement

Both records preserve the same product truth: a photo is optional/pending evidence, never
technical verification, and removing capture must not delete or rewrite existing private
records, provenance or pending state.

Both require the replacement and retirement branches, before/after lock and permission
graphs, privacy/security/EOL ownership, fallback/no-photo behavior, migration evidence,
native/generated diffs, lifecycle interruption tests and fresh Android/iOS artifacts when
the affected graph changes. Both treat an unknown native effect conservatively.

There is no selected photo dependency in either record. Therefore the comparison cannot
establish whether Flutter's plugin/channel path or RN/Expo's package/config-plugin path has
the smaller native impact for this product. A photo package name, candidate version or
documented API behavior would not close that gap without the resolved transitive native
graph and generated output.

Disposition: `TIE — BOTH HELD`; no candidate-specific replacement/retirement advantage is
proven.

### 4.3 Android-first release path

Both records allow Android to be released first only after an independent Android closure:

- current Google requirement and retrieval date;
- exact framework/runtime/package/native/config/generated/toolchain inputs;
- clean artifact and digest bound to the provenance/SBOM graph;
- owner-controlled Android plus constrained and main Android observations;
- permission denial, optional-photo/no-photo, process death, offline, low storage,
  reconciliation and safe-stop cases;
- TalkBack, text-size, focus/order, non-color state and Turkish critical-flow evidence;
- signing, Play account/staged testing and independent release verification.

The owner's Android phone is a real-device opportunity for both, not an observed pass for
either. Neither finalist record contains a build, install, TalkBack session, artifact
digest, signing record or Play evidence. Android-first narrows immediate external dependency
for both equally; it does not distinguish Flutter from RN/Expo.

Disposition: `TIE — BOTH HELD`; no Android-first framework delta is evidenced.

### 4.4 Later iOS rebuild and signing

Both records require a later, separate iOS lane with:

- an identified local Mac or explicitly approved hosted/alternate macOS route;
- exact Xcode/macOS/Apple SDK and framework/native package-manager inputs;
- regenerated native project and clean archive/IPA with digest and provenance;
- bundle identity, Team, certificate/profile/entitlement custody and rotation/recovery;
- oldest supported-end and current standard iPhone real-device sessions;
- VoiceOver, Dynamic Type/largest text, lifecycle interruption, permission, offline,
  restore, privacy and safe-stop evidence;
- App Store Connect/TestFlight and owner legal actions when the release window requires them.

Flutter's record explicitly calls out the Xcode/macOS requirement and the fact that a
borrowed iPhone does not supply the build/signing lane. RN/Expo's record reaches the same
boundary and excludes closing iOS with an Android artifact, simulator or non-exportable
hosted log. Neither has a Mac, archive, signing custody, TestFlight record or real-iPhone
AT result.

The absence of a Mac is therefore a shared current hold, not a Flutter or RN/Expo loss.
If a future provider works only as opaque EAS state, only as a secret manual workstation,
or only by shifting repair to the owner, that route fails the common control rule; the
framework outcome would then depend on the candidate's provider-independent fallback
evidence, not on a label such as “hosted.”

Disposition: `TIE — BOTH HELD`; no later-iOS or signing advantage is evidenced.

### 4.5 Accessibility and lifecycle maintenance

Both records require platform-specific evidence for the same difficult states:

- permission denial/grant/reset and native picker behavior;
- lock, call, background/suspension and process termination;
- durable checkpoint as context only, `unknown/partial` physical progress and accessible
  revalidation before continuation;
- offline package integrity, low storage, interrupted transfer and foreground reconciliation;
- TalkBack/VoiceOver, largest text, focus and reading order, Turkish warnings/status,
  non-color state, reduced motion and selected switch/voice controls;
- backup/restore, key loss, re-authentication, privacy classification and safe-stop.

Flutter assigns these to Dart state plus plugin/platform-channel, Kotlin and Swift
boundaries. RN/Expo assigns them to JS state plus config-plugin/prebuild/native module,
AppState and Kotlin/Swift boundaries. These are implementation ownership descriptions, not
observed behavior. Framework accessibility APIs and lifecycle hooks cannot substitute for
actual device evidence or qualified review.

The candidate records do not demonstrate different defect rates, accessibility semantics,
process-death behavior, reviewer load or upgrade outcomes. A claim that one surface is
“more coherent” or “more mechanically visible” remains an inference until the same event is
implemented and independently challenged.

Disposition: `TIE — BOTH HELD`; no accessibility/lifecycle maintenance delta is closed.

### 4.6 Hosted Mac optionality

The provider-independent hosted control review applies the same adversarial questions to
both candidates: legal owner versus build identity, least privilege, secret custody,
source/data exposure, artifact/log retention, machine-readable export, restore, outage,
plan/price/overage caps, account recovery, provider termination and exit.

Flutter's record leaves a hosted route conditional and provider-neutral. RN/Expo's record
mentions EAS as one possible hosted or local-with-EAS route but expressly does not make EAS
mandatory. That mention is not approval, a price quote, a capacity guarantee or a provider
advantage. Expo Go and OTA are excluded; a hosted route that requires either would violate
the common boundary.

No provider has been selected, no current price/limits/terms snapshot has been retained,
and no credential-custody/export/restore drill exists for either candidate. The hosted Mac
question cannot decide the framework while the provider and local fallback are unresolved.

Disposition: `TIE — BOTH HELD`; hosted optionality is a shared gate, not a scoreable benefit.

### 4.7 Provider/local recovery and exit

Both candidates define the same minimum recovery shape:

- owner-controlled/local Android route first;
- conditional local Mac route if reliable access later exists;
- hosted Mac only after explicit cost, credential, export and exit approval;
- portable source, lockfiles, config, generated/native inventory, toolchain recipe, SBOM,
  artifacts, logs, evidence and data/migration contracts outside the provider;
- last-known-good artifact retained;
- provider outage/account lock/quota exhaustion produces Android continuation where its own
  lane is closed and visible iOS `HELD`, never an OTA/Expo Go/manual-secret shortcut;
- irreversible data changes use forward migration and quarantine, not a binary rollback
  that silently loses history or provenance.

Neither record demonstrates a clean restore, export readability, digest comparison, provider
outage rehearsal, account recovery, signing rotation or alternate-host rebuild. Thus neither
has earned a provider-independent recovery advantage. A smaller-looking export list would
not be an advantage if it hides generated/native, signing or authority inputs.

Disposition: `TIE — BOTH HELD`; recovery remains unproven for both.

### 4.8 Store-rule churn

Both records correctly treat Apple/Google requirements as release-window inputs rather than
permanent promises. Both freeze the last safe artifact, re-resolve framework/toolchain,
dependency and native inputs, regenerate affected outputs, rebuild/re-sign, re-run platform
evidence and retain the prior artifact until independent verification.

The candidate-specific churn surfaces differ in kind:

- Flutter may require coordinated Flutter/Dart SDK, pub resolution, plugin/native host,
  generated registrant, Gradle/Android and Xcode/SwiftPM or CocoaPods updates.
- RN/Expo may require coordinated Expo SDK/RN/React/Node, package/native sub-locks,
  effective app config, config-plugin/prebuild templates, generated Android/iOS projects,
  Gradle/Android and Xcode/SwiftPM or CocoaPods updates.

RN/Expo's compatibility line can create a visible SDK/config-plugin/prebuild coupling;
Flutter's plugin and host integration can create a visible Dart/native/package-manager
coupling. Neither document includes a real forced requirement event, resulting diff,
rebuild time/failure, artifact comparison or support/EOL decision. Therefore the form of
the churn is known, but its candidate-attributable burden is not.

Disposition: `TIE — BOTH HELD`; no store-rule-churn winner is evidenced.

## 6. Tie status and decision rule

The proper current decision is:

`FLUTTER HELD` + `RN/EXPO HELD` -> `TIE NOT BREAKABLE / FRAMEWORK SELECTION HELD`

This is not “both are equally good” and not a numerical tie. It means the evidence set does
not expose a material, candidate-attributable difference that survives the critical controls.
The two closure records describe different technical boundaries, but description alone does
not show which boundary is easier to rebuild, maintain, audit, recover, afford or release
for Kavriva.

The following future outcomes are disqualifying or holding rules, applied symmetrically:

- Expo Go, OTA/runtime code delivery, an opaque provider-only native state, plaintext keys,
  unknown signing identity, non-exportable artifact/provenance, unbounded charge or owner
  debugging is `REJECT` where no safe fallback exists.
- Missing lock/hash, unexplained generated/native output, absent Mac/build route, missing
  real-device/AT/safety/release evidence, unresolved provider terms/caps or absent recovery
  is `HELD`.
- A closed Android lane may proceed first while the other platform remains visibly `HELD`;
  this does not close the overall framework comparison or excuse the later iOS lane.

No conditional framework recommendation should be written until one candidate closes these
critical controls with the same event, fixture, owner model and independent challenge. The
future decision must use material evidence and explicit gates, not a weighted convenience
score or a raw packet/count comparison.

## 7. Minimum evidence that could break the tie

The next exercise must produce the same evidence classes for each candidate. It may break
the tie only if the result shows a material difference; it must not manufacture a winner
from missing or common evidence.

1. Freeze T0 and the simultaneous photo/build-requirement event, select replacement versus
   retirement, and preserve old artifact/data/provenance.
2. Resolve exact framework/runtime, direct/transitive package locks, native sub-locks,
   source hashes, toolchains, permissions, entitlements, configuration and security/EOL
   ownership.
3. Produce the candidate-specific generated/config/native diff and a clean regeneration
   recipe. Every output must be tied to a pinned input; unexplained output holds the lane.
4. Rebuild Android from the portable closure, bind artifact digest/SBOM/signing/provenance,
   run the owner Android plus constrained/main cohorts, and obtain independent lifecycle,
   accessibility, safety and Play evidence.
5. Rebuild iOS through a confirmed local or explicitly approved hosted/alternate Mac route,
   bind archive/IPA/signing/provenance, run oldest/current iPhone and VoiceOver/Dynamic
   Type evidence, and complete the owner/TestFlight/App Store actions required at that
   release window.
6. Export and restore the full packet outside the build provider, compare digests and
   inputs, rehearse provider outage/account lock/quota exhaustion, and show Android-first
   continuation plus safe iOS hold.
7. Capture official current store/framework/provider terms, price, quota, overage, tax/FX,
   retention, credential and exit evidence; place each cost in the staged mandatory,
   deferrable, optional, scale-triggered or contingency worksheet before approval.
8. Have an independent adversarial reviewer verify candidate-attributable differences and
   confirm that no documentary claim is being presented as a build/device/AT pass.

Until these conditions are met, the correct action is to keep both finalists available for
the next no-code evidence step and keep framework selection `HELD`.
