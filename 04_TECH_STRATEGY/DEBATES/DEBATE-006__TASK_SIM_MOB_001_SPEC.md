# DEBATE-006 — TASK-SIM-MOB-001 COMMON SPEC

Status: `CONTROLLED NO-CODE SIMULATION FIXTURE / GROUP A`
Date: 2026-09-18
Candidates: Flutter; React Native + Expo development builds; KMP + Compose Multiplatform

## 1. Purpose

Compare how a fresh AI would safely plan one identical Kavriva change without reading the whole project or writing code.
This is not a prototype, effort estimate, benchmark or implementation authorization.

## 2. User-Visible Change

Add one safety-critical active-maintenance step that:

- is available from a valid selected-motorcycle/task offline package;
- shows task objective, warning and readiness state in Turkish;
- accepts an optional photo without turning the photo into verification;
- saves only an explicit durable checkpoint;
- survives lock, call, backgrounding and process termination;
- restores the last durable checkpoint as context, not physical truth;
- marks uncommitted work `unknown/partial`;
- requires accessible physical-state revalidation before continuation;
- always preserves safe-stop/recovery;
- produces Android and iOS release/test evidence without OTA code delivery.

No real motorcycle-specific torque, part, fitment or safety value is invented in the simulation.

## 3. Fixed Starting State

- motorcycle/model-year/variant context is resolved;
- one approved task package generation is installed and within its allowed offline window;
- compact required closure is available; optional heavy media is absent;
- local account-light history exists;
- camera permission is not yet granted;
- network changes from constrained cellular to offline after the step opens;
- the OS terminates the process after a photo is captured but before the next checkpoint commits;
- after restart, the task package is still locally intact and no new server recall knowledge is available;
- screen reader is enabled and largest text is used on the accessibility path.

## 4. Required State Outcomes

| Event | Required truth |
|---|---|
| Step opens | Objective, warning, readiness and safe-stop are available offline |
| Camera denied | Step remains usable where photo is optional; denial is explained accessibly |
| Photo captured | Photo is pending evidence, not verification or committed physical truth |
| Process termination before checkpoint | Photo/temp work may need recovery; physical progress is `unknown/partial` |
| Restart | Last durable checkpoint restores; no automatic continue |
| Revalidation | User confirms required current physical observations through accessible controls |
| Revalidation fails/uncertain | Application remains held and safe-stop/recovery stays available |
| Revalidation succeeds | Next allowed transition opens and a new explicit checkpoint may commit |
| Reconnection | Foreground reconciliation checks package/release/recall eligibility before further authority |

## 5. Required No-Code Work Packets

Every candidate must produce the minimum sufficient context for:

1. shared product/state contract packet;
2. shared UI/presentation packet;
3. local persistence/checkpoint/migration packet;
4. camera/photo/temp-file/privacy packet;
5. Android lifecycle/accessibility packet;
6. iOS lifecycle/accessibility packet;
7. offline package/reconciliation compatibility packet;
8. automated contract/state/negative-test packet;
9. real-device human acceptance packet;
10. build/signing/provenance/release-evidence packet;
11. independent review packet;
12. exit/rollback-refusal/forward-recovery packet.

Packets may be combined only when the candidate proves the combined context remains bounded and does not hide platform,
authority or reviewer separation.

## 6. Required Record Per Packet

- purpose and user outcome;
- minimum input documents/contracts;
- allowed files/modules to change;
- forbidden scope;
- upstream/downstream dependencies;
- candidate-specific dependency, generated file or native boundary;
- Android/iOS divergence;
- acceptance and negative cases;
- evidence artifact;
- implementer/reviewer/validator separation;
- external human/store/device action;
- failure and recovery;
- unresolved cost/capacity trigger;
- Obsidian-compatible links to requirements, screens, contracts, tasks and tests.

## 7. Comparison Questions

The simulation must answer without scoring:

- how many distinct context types must a fresh AI understand;
- where a routine shared change splits into Android/iOS work;
- what generated/native files can change indirectly;
- whether a failed candidate-specific dependency can be replaced behind a boundary;
- what must be rebuilt and revalidated;
- which evidence can be automated and which needs physical devices/humans;
- how another AI detects incomplete cross-platform parity;
- whether the task can be reverted without lying about already-migrated data or physical state;
- what survives framework replacement.

Raw packet count is not a winner by itself. Hidden or overloaded packets are worse than explicit bounded packets.

## 8. Automatic Failure Conditions

- asks the owner to code, debug or repair a build;
- restores UI state as proof of current physical state;
- treats an optional photo as technical verification;
- depends on scheduled background work or push for correctness;
- omits either Android or iOS lifecycle/accessibility work;
- lets a plugin/module/generated project bypass dependency and release evidence;
- uses OTA code delivery;
- downloads unrelated motorcycle/catalog content;
- lacks safe-stop/recovery or a forward-recovery path;
- claims a device/build/accessibility pass from documentary simulation.

## 9. Candidate Output Status

Each candidate simulation ends with:

- `OPERABLE IN PRINCIPLE / HELD FOR EVIDENCE`,
- `OPERABLE WITH MATERIAL CONDITIONS / HELD`, or
- `NOT OPERABLE UNDER CURRENT MODEL`.

No candidate becomes selected from this simulation alone. Two independent critiques and manager synthesis remain required.
