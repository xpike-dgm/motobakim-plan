## 2. Areas of Agreement

Both independent reviews agree that:

1. framework choice does not supply Kavriva's offline truth, recall, migration, authorization, release or safety model;
2. every option still requires Android/iOS lifecycle, real-device, accessibility, signing and incident evidence;
3. one shared UI can reduce routine duplicate edits but can hide native exceptions;
4. native UI can expose platform behavior directly but does not remove duplicated implementation and parity work;
5. provider, hosted-build or free-tier cost cannot be treated as zero without cap, alert, export and exit evidence;
6. the user cannot be made responsible for debugging, signing failures or generated/native project repair;
7. no aggregate score or unconditional five-way winner is currently defensible.

## 3. Judge Grouping

### Group A — Shared application/presentation surface

- Flutter;
- React Native + Expo development builds with explicit native boundary;
- KMP + Compose Multiplatform.

This group can represent routine UI/application work once for Android and iOS. Under the approved solo-owner,
AI-operated and limited-budget model, that is a material direction-level advantage because fewer duplicate feature
packets and parity edits are expected. It is not proof of lower total cost: native hosts, device evidence and two signed
store artifacts remain.

### Group B — Two explicit native UI ownership paths

- KMP-native shared domain/data plus native Android/iOS UI;
- fully native Kotlin/Android plus Swift/iOS.

These options make platform behavior and native semantics more direct. They also require two UI implementations, two
accessibility correction paths and two feature/release parity streams. KMP-native reduces some domain/data duplication
but adds Kotlin/Native framework integration; full native removes a cross-platform runtime but duplicates more of the
product graph.

### Current judge disposition

Group A proceeds to a focused no-code AI-task simulation first. Group B remains the direct-platform/reference baseline
and is not rejected. It becomes leading only if the focused simulation proves that shared-UI native boundaries are less
operable/recoverable than the explicit duplicate paths or if direct platform evidence materially outweighs the duplicate
capacity burden.

This is a justified evidence order, not a framework selection.

## 4. Conditional Positions Inside Group A

| Candidate | Becomes stronger if | Becomes weaker if |
|---|---|---|
| Flutter | Shared visual/state work remains bounded in Dart and critical plugins/native adapters are pinned, owned and replaceable | Plugin/channel/host drift or iOS lifecycle/accessibility exceptions cannot be reproduced and reviewed |
| React Native + Expo | TypeScript/React task boundaries are deterministic, generated native output is controlled, and browser-tool adjacency is deliberately proven without merging trust domains | Expo Go/OTA shortcuts appear, prebuild/config/native module output is opaque, or hosted-build coupling lacks cap/export/exit |
| KMP + Compose | Kotlin/Compose/Gradle/Xcode graph is reproducible and iOS semantics/native escape are independently validated | Compiler/runtime/generated-framework coupling or iOS accessibility/native integration creates an unowned specialist path |

The evidence does not yet support ordering these three. Browser-based Internal Operations does not itself select
TypeScript/React, and language adjacency is not counted until the web boundary is deliberately chosen and proven.

## 5. Next Equal No-Code Simulation

The three Group-A candidates receive the same representative `TASK-SIM-MOB-001`:

> Add one safety-critical active-maintenance step that works offline, saves a durable checkpoint, accepts an optional
> photo, survives process termination, returns through a Turkish accessible revalidation/stop flow, and produces both
> Android and iOS release evidence without OTA.

For each candidate, the simulation must produce without code:

- minimum sufficient AI context pack;
- exact task/module/contract boundaries;
- shared versus Android-specific versus iOS-specific work packets;
- dependency/native/generated-file changes;
- required independent review and validation packets;
- failure, rollback/forward-recovery and exit effects;
- external actions the nontechnical owner must perform;
- unresolved cost/capacity triggers;
- proof that a fresh AI can execute each packet without whole-project context.

The simulation does not estimate fictional developer hours and does not claim productivity. It compares change surface,
context fragmentation, native exception visibility, deterministic evidence and recovery burden.
