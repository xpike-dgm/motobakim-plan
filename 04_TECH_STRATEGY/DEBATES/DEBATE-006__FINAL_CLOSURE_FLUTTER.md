# DEBATE-006 — FLUTTER FINAL CLOSURE EXERCISE — DOCUMENTARY / NO-CODE / HELD

Status: DRAFT / DOCUMENTARY / NO-CODE / EQUAL CLOSURE FIXTURE / HELD  
Date: 2026-09-18  
Candidate: Flutter shared Dart UI/application surface with explicit Android/Kotlin and iOS/Swift native boundaries  
Decision level: Phase-4 comparison evidence only; not a recommendation, ADR, implementation, paid-service approval or Gate 4 -> 5 transition

## 1. Meaning of this exercise

This is the final tie-break exercise requested after the equal TASK-SIM-MOB-001 simulation. It examines whether a
fresh AI-operated delivery system can make a simultaneous native-dependency and build/release change visible,
bounded, reviewable and recoverable for Flutter.

The exercise is documentary only. It creates no application code, prototype, proof of concept, executable spike,
build, benchmark, store submission or device pass. The filenames and packet IDs below are an evidence plan, not a
claim that an implementation repository already exists.

HELD has a precise meaning here:

- the closure plan may be complete enough to review, but no critical lock, generated/native inventory, signed
  artifact, real-device/accessibility result, independent review, price or owner capacity is being treated as closed;
- a missing Mac, dependency owner, physical-device session, qualified safety/content reviewer, signing custodian or
  accepted cost route holds the affected lane;
- the nontechnical owner is never asked to code, debug, repair Gradle/Xcode, operate signing secrets or waive a
  safety/accessibility/release requirement.

The exercise must be run with the same event envelope for the other finalist. Raw packet count is not a score. A
smaller packet graph is not a benefit when it hides native, generated, authority or reviewer work.

The following facts are inherited and are not silently changed:

- The owner directly controls an Android phone.
- iPhones may be borrowed from close friends for testing, but borrowed access is not a permanent release dependency.
- No owned or reliably accessible Mac has been confirmed.
- A hosted Mac/build route is a later option only, subject to a current quote, explicit approval and provider-independent
  recovery.
- Approximately TRY 2,000–3,000 per month is a future non-store planning ceiling, not current spend authorization,

- Google Play Console and Apple Developer Program store fees are already accepted as mandatory release costs under

- Both platforms remain in scope for this equal exercise even though publication is staged.
- Expo, Expo Go, OTA code delivery and any framework-specific OTA shortcut are out of scope. This is a Flutter record.

Frozen comparison inputs remain those in the common fixture:

- Flutter comparison snapshot: 3.47.2 stable with bundled Dart 3.13.2 and the recorded official release ref/digest.
  The snapshot is not silently replaced by newer metadata; a later ADR must re-pin SDK, Dart, ref, digest and
  toolchain together.
- Four cohorts: constrained Android API 29 / 4 GB RAM / 64 GB storage / 2 GB free; main Android 13+; oldest

## 3. Simultaneous change event

The exercise has one baseline and two changes that arrive as one release-impact event. Both changes must be traced
before either one is called complete.

### 3.1 Baseline T0

At T0 the product has an optional-photo path behind a Flutter-facing adapter. The concrete camera, image-picker,
file-import or share package is intentionally not selected by this exercise. The baseline evidence records:

- direct and transitive dependency graph and each source/provenance reference;
- Android and iOS plugin implementations, generated registration and native configuration;
- permission/privacy declarations and temporary-file behavior;
- pending-evidence schema and the no-photo fallback;
- Flutter/Dart SDK, Android and iOS toolchain locks;
- generated/config/native inventories and exact artifact provenance;
- Android and iOS device/accessibility/release evidence status.

The baseline artifact is retained. It is not overwritten by the change event.

### 3.2 Change A — optional-photo dependency changes or is retired

The exercise must run both branches because a product decision may replace the dependency or abandon the optional
photo capability.

Branch A1 — replacement:

- The current photo dependency is judged abandoned, incompatible, insecure, unowned or otherwise unacceptable.
- A replacement may be another reviewed package or an owned Kotlin/Swift adapter, but no package is presumed.
- The Kavriva-owned media adapter contract and pending-evidence meaning must remain stable.
- Existing photo records, provenance and privacy scope remain; the replacement is not permission to rewrite or delete
  past evidence.
- The replacement's complete direct/transitive Android and iOS graph, licenses, EOL/security response, native
  implementation, generated registration and fallback owner must be named.

Branch A2 — retirement:

- New photo capture/import is removed from the active step, or the optional-photo capability is retired.
- The no-photo path becomes the explicit supported path; it must not make the step unsafe or less recoverable.
- Existing private/shared records and pending operations are preserved under the approved privacy and migration rules.
- A capability/configuration flag that changes user-visible meaning is a controlled release input; it cannot be an
  unreviewed remote binary replacement or a way to clear an emergency suspension.
- Removal must prove absence from both platform dependency and permission graphs. “The screen no longer shows it” is
  not sufficient evidence.

For both branches, a captured photo never becomes technical verification, physical truth or a durable checkpoint by
itself.

### 3.3 Change B — Apple/Google build requirement changes at the same time

The exercise does not invent a future minimum version or pretend a current store rule is permanent. At the event,
the current official Android/Google and Apple requirements are captured, compared with the T0 release envelope and
classified. Possible classes include:

- minimum OS/deployment target or supported architecture;
- Android SDK/NDK/build tools, AGP, Gradle, Kotlin or JDK;
- Xcode/macOS, iOS SDK, Swift/SwiftPM or fallback CocoaPods requirements;
- Android manifest, privacy, permission or package-registration requirements;
- iOS Info.plist, entitlements, privacy manifests, bundle ID or provisioning requirements;
- store upload tool, account verification, testing-track or App Store Connect/TestFlight requirement;
- signing-key, certificate, provisioning, upload or developer-identity requirement.

No exact future value is written into this fixture. The new official requirement and retrieval date become release
inputs, and the old requirement remains in the provenance record so the impact is auditable.

The event is intentionally simultaneous: a photo dependency change cannot be closed while the changed store/build
requirement is ignored, and a toolchain change cannot be closed while the dependency/native graph is unknown.

## 4. Closure graph and file-class inventory

The closure object is the exact relationship graph from source and product meaning to platform artifacts and store
evidence. Every class is recorded as present, removed, changed, generated, environment-only, secret-bearing or
not-applicable. “Not applicable” needs a reason and reviewer confirmation; it is not an empty field.

### 4.1 Lock and manifest classes

| Class | Examples to enumerate | Closure question |
|---|---|---|
| Product and release meaning | photo capability contract, no-photo fallback, pending-evidence schema, migration version, offline package manifest, client capability, API/schema/content/configuration/revocation generations | Did the event change product meaning, offline eligibility, privacy or recovery truth? |
| Flutter SDK/Dart | Flutter channel/version, exact git ref and digest, bundled Dart version, SDK provenance, supported-platform snapshot | Is the same SDK reproducible, and did the build requirement force a re-pin? |
| Dart package resolution | pubspec.yaml, direct dependencies, dependency constraints, dependency_overrides, pubspec.lock, package source/ref/checksum, generated package configuration | Which direct/transitive nodes were added, removed or resolved differently? |
| Android build graph | Gradle wrapper, settings and root/app build files, version catalog if used, gradle.properties, dependency lock/resolution, repositories, checksums, AGP, Gradle, Kotlin, JDK, Android SDK/NDK/build-tools | Can an Android artifact be rebuilt from declared and verified inputs without hidden local state? |
| iOS build graph | Xcode version, macOS host, iOS SDK/deployment target, Swift/SwiftPM resolution, Package.resolved if used, Podfile/Podfile.lock and Pods resolution if fallback is used | Which native package manager and host versions are actually part of this artifact? |

Flutter's official dependency guidance states that pubspec.lock records the exact direct and transitive versions for
an application. The same guidance warns that a plugin may carry Kotlin/Java and Swift/Objective-C host code, so a
package edit is not a Dart-only edit. See the source register at the end of this document.

### 4.2 Generated and derived classes

Generated/derived material is not allowed to become an invisible side effect. The exact path set is unresolved until
the implementation repository exists, but the classes below must be enumerated and hashed or otherwise identified:

- generated Dart package configuration and dependency metadata;
- generated Flutter plugin registrants for Android and iOS;
- Flutter-generated native bridge/channel glue;
- Flutter-generated framework or Swift Package integration, including the generated Flutter plugin Swift package where
  applicable;
- generated Android resource/manifest/build-model outputs and generated registration;
- generated iOS workspace/project integration, build settings, schemes and package integration;
- CocoaPods-generated project support files if a dependency still requires CocoaPods;
- ephemeral Flutter framework/build outputs that are not source authority but affect the exact artifact;
- release archives, intermediate framework outputs, symbol files, mapping files and derived package manifests.

Generated output rules:

1. A generated file may be reproducible output, but it is still a release-impact surface.
2. A changed generator, plugin, SDK, package-manager resolution or host configuration triggers a generated-output
   diff and the affected platform rebuild.
3. An output that cannot be regenerated, explained and tied to a pinned input is a closure defect and holds release.
4. Generated output is never a place to hide a manual permission, entitlement, signing or dependency change.
5. Exact generated paths, commit policy and retention policy remain implementation decisions, not assumptions of this
   exercise.

Flutter's current Swift Package Manager guidance says SwiftPM is on by default from Flutter 3.44, Flutter falls back
to CocoaPods for dependencies without SwiftPM support, and migration can update Xcode project/scheme integration.
Therefore a photo dependency change may alter iOS package-manager files even when Dart source is unchanged.

### 4.3 Config and native classes

Android classes:

- AndroidManifest permissions, queries, exported components and provider declarations;
- Kotlin/Java media, lifecycle, storage, secure-key, notification, transfer and channel adapters;
- Android resource strings used by permission/privacy or recovery surfaces;
- Gradle and Kotlin build configuration, namespace/application ID, min/target/compile SDK, packaging and shrinker rules;
- network-security, backup/data-extraction and file-provider configuration where applicable;
- WorkManager/background configuration if present, with no timing guarantee used for correctness;
- debug/release/profile flavor configuration and signing references;
- test/instrumentation configuration and device matrix metadata.

iOS classes:

- Runner project/workspace and project.pbxproj settings;
- shared schemes and build configurations;
- xcconfig files, generated Flutter configuration and build scripts;
- Info.plist camera/photo/privacy and URL declarations;
- entitlements, capabilities, app groups and background modes where applicable;
- Swift/Objective-C media, lifecycle, key, notification, transfer, share and channel adapters;
- SwiftPM package graph and Package.resolved, or CocoaPods files/lock/resolution when fallback is required;
- privacy manifests and resource bundles where a dependency requires them;
- signing Team, bundle ID, provisioning and release configuration references;
- XCTest/host test configuration and device matrix metadata.

Cross-platform native classes:

- platform-channel contract and serialization;
- camera/picker/file/share behavior and URI/temp-file lifetime;
- app lifecycle/process termination and durable-checkpoint observation;
- Android Keystore and iOS Keychain adapters;
- foreground reconciliation and background-transfer hints;
- notification/deep-link intake, explicitly non-authoritative;
- backup/restore/clone and key-loss handling;
- native accessibility semantics, permission dialogs and system UI return focus.

The common state truth remains shared. Native observations, OS timing, permission result, key state, backup result
and system UI behavior remain platform-specific evidence inputs.

### 4.4 Signing, provenance and evidence classes

The release graph also records:

- source revision and review identity;
- Flutter/Dart ref and digest;
- pubspec and pub lock plus package source/provenance;
- Android dependency/toolchain/config/generated-output inventory and digest;
- iOS dependency/toolchain/config/generated-output inventory and digest;
- builder/host identity and environment/toolchain digest;
- SBOM, license/EOL/security review and exception/hold records;
- Android artifact type and digest, iOS archive/IPA and digest, symbols and mapping files;
- signer/certificate fingerprints and store account/track identity without exposing private keys;
- package/content/API/schema/configuration/revocation generations;
- Android/iOS automated, real-device, accessibility, safety/content, review and store evidence IDs;
- approval, hold, rollout/pause, incident and recovery links.

The provenance graph must show which files are source, which are generated, which are environment inputs and which are
secrets. It must never copy private signing keys, passwords, Apple API keys or Android keystores into the repository or
an unapproved evidence packet.

## 6. Rebuild and revalidation trigger matrix

“Rebuild” means a new exact platform artifact from pinned inputs. “Revalidate” means rerun the evidence classes
affected by the change. A shared Dart change does not excuse platform evidence.

| Trigger | Artifact consequence | Generated/config/native effect | Evidence that must rerun | Recovery/hold |
|---|---|---|---|---|
| Flutter SDK, engine or Dart ref/digest changes | Rebuild Android and iOS artifacts | Flutter framework outputs, plugin registrants, host integration and symbols may change | Both automated contract/state tests; both platform device/AT/release evidence where behavior can differ | Retain T0 artifact; hold until SDK/toolchain graph is pinned and reviewed |
| Direct Dart dependency or pubspec constraint changes | Rebuild both artifacts when the dependency is in the mobile graph | pubspec.lock, generated package config and any plugin registration/native graph | Lock diff, SBOM, licenses, clean-build and affected runtime/AT evidence | No override or silent solver drift; forward-fix only |
| Transitive pub lock or package source changes | Rebuild both affected platform artifacts | Native implementation and generated outputs may change even if Dart import does not | Dependency provenance/EOL/security, generated diff, runtime and store artifact evidence | Hold if source, maintainer, fallback or impact is unclear |
| Photo dependency replacement | Rebuild both Android and iOS for a dual-platform capability | Camera/picker implementations, permissions, privacy manifests, channel registration, temp-file behavior | Camera deny/grant, optional no-photo path, pending evidence, process kill, privacy, AT and both device lanes | Keep T0 artifact and old records; no silent substitution |
| Photo capability retirement | Rebuild both if client behavior or native graph changes | Remove dependency, registration, permissions, picker config, generated outputs and privacy declarations | No-photo safety/recovery, old-photo/history preservation, migration, privacy and negative evidence | If removal would lose truth or safe fallback, hold capability; do not delete records |
| Platform-channel or Kotlin/Swift adapter changes | Rebuild only directly affected artifact plus parity review; this exercise's dual change affects both | Native source, serialization, registration, project integration and symbols | Platform interruption, permission, key, lifecycle, AT and security evidence | Isolate adapter behind contract; hold on unowned native behavior |
| Android SDK/AGP/Gradle/JDK/manifest requirement changes | Rebuild Android artifact | Gradle resolution, manifest, resources, shrinker, packaging and generated outputs | Clean Android rebuild, constrained/main device, TalkBack, app bundle/signing and Play readiness | Android lane held on unavailable toolchain or account; iOS remains separately evaluated |
| iOS/macOS/Xcode/iOS SDK/SwiftPM or CocoaPods requirement changes | Rebuild iOS artifact | Runner, schemes, xcconfig, entitlements, Package.resolved/Podfile.lock and generated package integration | Clean iOS archive, oldest/current iPhone, VoiceOver, signing and App Store Connect/TestFlight readiness | Hold without local/approved hosted Mac; do not downgrade requirement silently |
| Permission, privacy manifest, entitlement or background-mode change | Rebuild affected platform artifact | Manifest/Info.plist/entitlements and possibly generated package output | Denial/reset, native dialog AT, privacy disclosure, lifecycle and store review evidence | No permission bypass; affected feature held if disclosure or review is incomplete |
| Generated output differs without an explained input | Rebuild affected artifact after root-cause analysis | Generated registrant, project/workspace, package or build files | Regeneration diff, clean rebuild, SBOM/provenance and parity review | Closure defect; hold until explained and archived |
| Signing certificate, upload key, provisioning, Team or store identity changes | Re-sign and rebuild affected artifact | Signing config, bundle/package identity, provisioning and release metadata | Key custody/recovery, artifact digest, store validation and staged release | Preserve old signed artifact; no key export or identity swap without owner authority |
| Build script, builder image, CI host or toolchain environment changes | Rebuild both if the release graph is shared; otherwise affected lane | Builder inputs, generated outputs, symbols, provenance and attestation | Clean reproducibility, artifact digest, SBOM and independent build review | Local/hosted provider change requires export and exit proof; unknown host is HELD |
| API/schema/migration/offline manifest/configuration generation changes | Binary rebuild only when client capability or interpretation changes; always rerun package/reconcile evidence | Release graph, migration and package-generation metadata | Compatibility, offline, recall, idempotency, migration and incident evidence | No lossy rollback; forward migrate or hold affected scope |
| Content-only correction or recall | No binary rebuild unless client meaning/configuration changes | Content/revocation generation and offline package artifacts | Qualified content/safety review, package integrity and foreground reconciliation | Safe-stop/hold offline; no notification or cached package as current authority |
| Store upload/test rule or developer-verification change | Rebuild/re-sign if artifact or metadata is affected; otherwise update store evidence | Store metadata, account verification, target SDK/build tool or testing-track records | Current official requirement snapshot, account/store evidence and owner action | Android-first may proceed only on a closed Android lane; iOS stays HELD if its lane is blocked |

For this exercise, the simultaneous photo and Apple/Google build event is a both-platform rebuild event unless the
impact graph proves a platform is genuinely untouched. “Shared source” and “Android-first” are not sufficient proof
of an untouched iOS artifact.

## 7. Android evidence packet

The Android lane is first in the staged publication order because the owner directly controls an Android phone. It is
not automatically a framework pass.

### A-01 Dependency and generated closure

The packet records:

- T0 and T1 direct/transitive dependency graphs, package source and provenance;
- replacement or retirement decision and the stable Kavriva media-adapter contract;
- Android plugin implementation and native library closure;
- manifest permissions, file-provider/URI and privacy-related declarations;
- generated plugin registration, generated resources, Gradle model and any shrinker/packaging effects;
- exact Gradle/AGP/Kotlin/JDK/SDK/NDK/build-tools and repository/checksum inputs;
- removed nodes as well as added nodes, so retirement cannot leave a dormant permission or native binary.

No package is selected by this plan. A candidate package without an owner, security/EOL response, native fallback and
device evidence remains HELD.

### A-02 Changed Android/Google requirement

At T1 an AI records the official current requirement and its retrieval date, then maps it to:

- Android API/device floor and architecture;
- compile/target SDK, AGP, Gradle, Kotlin, JDK, NDK/build-tools;
- manifest, permission, privacy, package-name and developer-account conditions;
- Android App Bundle, Play App Signing, upload key and release-track requirements;
- personal-account closed-test or device-verification conditions if applicable at the release date.

The value is not guessed from a prior release. Google Play's official guidance currently states that new personal
developer accounts created after 13 November 2023 need a closed test with at least 12 continuously opted-in testers
for 14 days before production access. That is a release coordination fact, not a permanent promise; it must be
rechecked when the event occurs.

Android developer verification and package-name/signing identity requirements are also treated as a possible
distribution-path trigger. The current Android guidance describes verification and package-name registration
requirements with staged rollout. Applicability, geography and timing are rechecked rather than hardcoded.

### A-03 Runtime and accessibility evidence

Separate later real-device sessions must cover:

- constrained Android API 29 and main Android cohort;
- camera denied, optional no-photo continuation, capture as pending evidence and picker cancellation;
- network transition from constrained cellular to offline, package integrity and no unrelated catalog download;
- lock, incoming call, background, process termination and restart;
- last durable checkpoint as context only, unknown/partial physical progress and accessible revalidation;
- revalidation failure/uncertainty with safe-stop retained;
- foreground reconnect check of package/client/configuration/recall authority;
- TalkBack, largest text, focus/order, warning and status announcements, non-color state, Switch/Voice Access where
  selected, reduced motion and reduced dexterity;
- low storage, pending operations, private photo/history scope, backup/restore and key-loss quarantine.

Automated Dart/state/contract reports may support these cases but cannot close native dialogs, process termination,
TalkBack or qualified safety/content review.

### A-04 Android signing and release evidence

The Android packet must link:

- exact source/lock/toolchain/config/generated-output manifest;
- clean-checkout rebuild record and artifact checksum;
- SBOM, provenance/attestation, license and security review;
- upload-key certificate fingerprint and Play App Signing identity/custody;
- AAB/APK artifact identity, version code, track and staged-release record;
- device/AT/safety/review evidence for the exact artifact;
- pause, recall, impact and forward-recovery record.

Android's official signing guidance distinguishes the upload key used to submit an App Bundle from the app-signing key
used by Google Play for distribution. A signing change is therefore a provenance and continuity event, not a file
replacement. Private keys remain outside the evidence repository.

### A-05 Android lane disposition

Android can be staged first only when its exact dependency/native closure, toolchain requirement, runtime, AT, safety,
signing and store evidence are closed. If iOS lacks Mac/build/device/evidence capacity, iOS remains HELD and the
Android release may be separately considered under the approved staged-release direction. This does not make the
equal Flutter closure exercise or the framework recommendation PASS.

## 9. Signing and provenance impact of the simultaneous event

The T1 artifact is a new release object. It cannot be described as T0 with a package swapped after signing.

Required graph:

source review -> Flutter/Dart pin -> pub lock and native dependency graph -> Android/iOS host/config/generated outputs
-> builder/toolchain identity -> automated evidence -> real-device/AT/safety evidence -> artifact digest -> signature
-> store target/track -> rollout/pause/revocation generation

Dependency replacement:

- adds new SBOM/license/EOL/security/provenance nodes;
- removes old dependency and permission/native nodes only after absence is verified;
- changes generated registration, native project integration or privacy declarations when applicable;
- requires new Android and iOS artifact digests and platform evidence;
- retains the T0 artifact and old provenance for incident impact and rollback refusal.

Dependency retirement:

- proves no new capture/import path is reachable;
- preserves old media records and pending operation provenance;
- applies forward migration to any stored capability/pending-photo state;
- does not use a remote flag to claim a binary was replaced or to clear a suspension;
- keeps the safe no-photo flow and revalidation closure.

Build requirement change:

- changes the builder/toolchain provenance even if application source is byte-for-byte unchanged;
- may change generated config, dependency resolution, deployment target, manifest/entitlements and artifact shape;
- forces the affected platform artifact to be rebuilt and re-signed;
- forces current store/account/upload evidence to be captured again;
- must preserve the prior accepted artifact until the new one is independently verified.

Signing identity change:

- is an owner/account authority event, not an AI workaround;
- requires custody, rotation/recovery, certificate continuity and store identity evidence;
- cannot expose raw keys in source, logs or generated evidence;
- holds release if the signer, account, provisioning or upload identity is unavailable.

No OTA code path is allowed. Content/configuration changes follow the approved release/publication/revocation graph
and cannot manufacture a new binary or current safety authority.

## 10. Local, hosted and forward recovery

### L0 — Owner-controlled Android route

The Android-first path uses the directly controlled Android phone for the first physical runtime and accessibility
oracle. The environment itself still needs to be verified: SDK/toolchain availability, signing custody, artifact
retention, device matrix and independent reviewer access are not assumed from phone ownership.

If the local Android environment is unavailable or untrusted, the Android lane is HELD rather than repaired by the
nontechnical owner. A future local/portable environment must consume the same source, lock, manifest, SBOM and
artifact evidence.

### L1 — Local Mac route if later confirmed

A local Mac route becomes eligible only after access, macOS/Xcode version, storage, signing custody, account role and
repeatability are documented. The iOS lane must still use the borrowed/current iPhone sessions and independent
review. A Mac being temporarily available for a single upload is not equivalent to a recoverable build path.

### H1 — Hosted Mac/build route if local Mac is not available

Hosted build is a conditional option, not a provider decision. Before approval, the owner receives:

- current official price and billing period in the applicable currency;
- tax/currency exposure, free/capped route, hard cap or overage shutdown and spend alerts;
- whether builds, logs, caches, artifacts and private source leave the intended trust boundary;
- signing-key/API credential handling, least privilege, rotation and revocation;
- export of source references, locks, generated manifests, SBOM, provenance, artifacts and logs;
- retention, deletion, account recovery and provider outage behavior;
- provider-independent local or alternate-host rebuild route;
- migration/exit path and the cost/capacity of leaving the provider.

No hosted amount is estimated here. The future TRY 2,000–3,000 non-store ceiling is a planning envelope only; a
hosted choice needs separate explicit approval and does not include store fees by implication.

### R1–R6 Forward recovery branches

| Failure | Required response | Forbidden shortcut |
|---|---|---|
| R1 Photo replacement fails | Keep the last accepted artifact, use the safe no-photo path if product-approved, quarantine affected capability and forward-fix behind the adapter boundary | Silent package substitution, photo-as-verification or forced owner repair |
| R2 Photo retirement migration is ambiguous | Preserve media/history/provenance, quarantine pending state and hold new capture until migration is reviewed | Silent deletion, last-write-wins or binary downgrade |
| R3 Android build requirement cannot be met | Hold Android release, preserve provider-independent inputs and current artifact, escalate only the external account/toolchain action | Unsigned APK/AAB, hidden local dependency or unsupported store target |
| R4 iOS Mac/build requirement cannot be met | Keep Android-first lane separate; hold iOS and present the priced host/local decision to the owner | Treat borrowed iPhone as a build substitute or use an unapproved host |
| R5 Signing/provenance fails | Stop release and retain the prior signed artifact; reconcile identity/custody and regenerate evidence | Copy keys into repository/logs or change identity without authority |
| R6 Runtime/AT/safety evidence fails | Keep safe-stop/recovery, mark the affected path HELD and rerun only after a reviewed fix-forward | Simulator claim, AI-only signoff, store submission with missing evidence |

At every branch, restore only the last durable checkpoint as context. Post-checkpoint physical work remains
unknown/partial until accessible current-state revalidation. A photo, UI restoration, push notification or cached
package does not create current authority.

## 14. What survives a Flutter replacement

Portable product truth:

- canonical state/transition contracts, Turkish copy intent, safety/readiness/safe-stop semantics and accessibility
  oracles;
- schemas, operation IDs, history/provenance, correction/withdrawal records, conflict and migration fixtures;
- scoped offline package manifests/digests, content/configuration/revocation generations and optional-media metadata;
- private/shared/community classification and user-controlled export subject to approved privacy/key policy;
- S1–S15 fixtures, TASK-SIM-MOB-001 evidence schema, parity matrix, SBOM/provenance and incident runbooks.

Flutter- or toolchain-bound surface:

- Dart widgets/state composition, Flutter engine/renderer and Dart runtime artifacts;
- pub/plugin APIs, platform channels and generated plugin registration;
- Android runner/Gradle/Kotlin/manifest/resource configuration;
- iOS Runner/Xcode/SwiftPM/CocoaPods/entitlement configuration;
- camera/picker/transfer/share/notification/lifecycle/key adapters and signed Android/iOS binaries.

Android Keystore and iOS Keychain private keys are not portable product data. Key loss requires quarantine,
re-authentication and re-encryption under the approved policy; exporting raw keys is forbidden. Replacement is a
forward migration to a reviewed, signed client, not a lossy rollback.
