## APPROVED PRODUCT RULES — MUST PRESERVE

### Inactive motorcycle != history lock

When a motorcycle becomes inactive:
- history remains readable,
- evidence/provenance remains reachable,
- correction/dispute access remains,
- basic export remains,
- historical critical safety/correction reach-back remains.

Routine reminders may stop for inactive motorcycles.

### Reactivation

Reactivation restores the same historical record/evidence context. Maintenance timing may require current mileage/use information and recalculation. An interrupted physical job must not automatically resume from old confirmations.

### Archive != delete != transfer

These meanings must be visually distinct.

- Archive/inactive: preserve history and trust context.
- Transfer: move/share defined historical scope; partial coverage must not look complete.
- Delete: destructive action for the user's applicable copy/scope; independent data boundaries must remain explicit.

Do not merge these into one generic `Remove motorcycle` action.

### Entitlement gates new activity, not truth/safety

A plan/capacity/entitlement boundary may stop **new routine activity** where product rules allow.
It must NOT retroactively lock:
- existing history,
- basic search/read,
- export,
- provenance/evidence,
- correction/dispute/error-flag paths,
- critical safety reach-back,
- required safe closure/recovery for already-started physical work.

Do not design a permanent paywall that traps the user away from their own records.

### No pricing invention

Phase 3 does NOT decide exact price, tier names, quota amounts or billing implementation.
Use neutral access/capacity language only where needed.

### Transfer truthfulness

Transfer scope must show:
- what records/evidence are included,
- gaps/exclusions where relevant,
- partial history != complete history,
- prior provenance/attribution remains traceable.

Do not imply ownership transfer automatically validates records.

### Delete truthfulness

Before destructive deletion, show affected scope clearly. Delete must not silently erase independent records owned/held by other actors or rewrite historical provenance elsewhere.

## GENERATE EXACTLY 5 NEW MOBILE VISUALS

### J01 — SCR-008 / Motorcycle Switch + Active/Inactive Management
Purpose: user switches between motorcycles and clearly understands active vs inactive state.

Required:
- simple motorcycle list, not garage analytics dashboard,
- one clearly active motorcycle,
- inactive motorcycle still shows history-access meaning,
- switching active motorcycle is explicit,
- routine reminders for inactive may be described as paused where relevant,
- critical correction/history access must not look disabled,
- no invented limits/prices.

### J02 — SCR-031 / Motorcycle Lifecycle
Purpose: user understands available lifecycle actions and consequences before choosing one.

Required:
- selected motorcycle context,
- distinct actions such as make inactive/archive, reactivate when relevant, transfer, delete,
- concise consequence text for each,
- archive/inactive clearly preserves history,
- destructive delete clearly separated from non-destructive actions,
- no giant settings menu / no card-per-detail clutter.

### J03 — SCR-032 / Transfer Scope & Coverage
Purpose: user reviews exactly what history/evidence will transfer and what may be missing.

Required:
- target/transfer context generic; do not invent identity details,
- included scope summary,
- evidence/provenance/corrections treatment visible,
- coverage gaps / exclusions explicit if present,
- `partial != complete` message,
- one dominant confirmation/review action,
- no implication that transferred data becomes verified merely by transfer.

### J04 — SCR-033 / Delete Scope & Warning
Purpose: user understands what deletion will remove before confirming.

Required:
- destructive state visually clear but calm,
- exact user-visible scope categories affected,
- archive/inactive alternative available if appropriate,
- independent/shared data boundary explained,
- irreversible consequence acknowledged,
- one final destructive CTA with confirmation pattern,
- do not use fear-wall styling,
- no silent wipe of unrelated/independent data.

### J05 — SCR-037 / New-Activity Entitlement Gate + Preserved Access
Purpose: a user hits a boundary for starting a new routine activity but can still access protected existing value.

Required:
- clearly state what NEW action is blocked/limited,
- immediately show what remains available: history, evidence/provenance, correction/dispute, export, critical safety/recovery as applicable,
- safe return path,
- optional generic `access option / plan` path may exist but no price/tier/quota invention,
- no dark pattern,
- no retroactive record lock,
- if a physical repair is already started, this screen must NOT strand the user from safe completion/stop/recovery.

## CLUTTER RULES

- One primary job per screen.
- Do not turn lifecycle into settings dashboard.
- Do not show pricing cards or feature-comparison grids.
- Do not use 5 equal-weight destructive/secondary CTAs.
- Preserve one dominant action zone.
- Protected access should be explained compactly, not as a wall of badges.
- Transfer/delete scope can use grouped lists but avoid nested cards.

## BEFORE EACH IMAGE — QA

Ask:
1. Is active/inactive meaning immediately clear?
2. Is inactive history/evidence/export/correction still visibly preserved?
3. Are archive, transfer and delete distinct?
4. Does transfer avoid implying complete/verified history when scope is partial?
5. Does delete respect independent/shared-data boundaries?
6. Does entitlement block only the relevant new activity rather than existing truth/safety access?
7. Is any exact price/quota/tier being invented?
8. Is the screen simple and consistent with L05A/V10?

If not, simplify before generating.
