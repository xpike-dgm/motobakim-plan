## MEVCUT GUVENILIR BAGLAM — TEKRAR SORMA

- Core priority kendi motosikletinde islem yapan beginner ve experienced owner'dir; basic record tracking de ilk product value icindedir.
- Professional/service initial direct target degildir; owner-invited collaboration participant olabilir. Role automatic `verified` status yaratmaz.
- Readiness stop'ta once assessment error check, self-remediation ve evidence-based re-validation vardir. Professional recommendation optional support; unverified critical condition mandatory application gate'tir.
- Teaching content ile current motorcycle application instruction ayridir.
- Evidence vocabulary basic olarak `user assertion / documented / reviewed / verified` mantigini tasir; verified claim context'e gore degisir ve outcome guarantee degildir.
- Selective ownership transfer explicitly partial/incomplete history olarak gosterilir; covered period/gaps visible, private untransferred content hidden kalir. Transfer sonrasi silent overwrite yoktur; correction proposal attributed/reviewable olabilir.
- Actual owner-copy deletion linked own data'yi kapsayabilir; previously transferred independent records otomatik etkilenmez.
- Community contribution withdrawal public content/personal info'yu kaldirir; de-identified safety-review trace kalabilir ve withdrawn published correction affected guide re-review gerektirebilir.
- Export source/provenance, evidence level, important corrections ve dates'i tasimalidir.
- Core paywall disinda kalmasi gereken degerler: required safety info/visuals/checks, operation completion steps, reasonable history, data export ve basic multi-bike separation.
- Large media archive, advanced comparative analysis ve extensive collaboration premium candidate olabilir; final price/tier/business model secilmedi.
- Freshness ozellikle safety notices, technical values ve changeable procedure order gibi application-critical claims icin gate olabilir. Stale teaching/reference kalabilir; critical application re-check'e kadar kapanabilir. Numeric threshold yoktur.
- Active-repair accessibility alternate modalities kullanabilir fakat safety warning, motorcycle fit, technical value, stop condition, post-operation check ve critical confirmation kaldirilamaz.
- Account-light first value mumkundur; persistent real record, cross-device continuation veya collaboration profile transition icin natural trigger olabilir. Existing local data'nin ne olacagi aciklanmalidir.

## ZORUNLU SORU HARITASI

### Q156-Q158 — Basic history vs expanded storage
- Free core'da `yeterli/makul history` kullanici icin hangi degeri mutlaka korumali?
- Media/evidence saklama hangi product value noktasinda `expanded` hissedilir?
- Premium limitation kullanicinin historical trust veya safety record'unu nasil bozmamali?

### Q159-Q161 — Basic multi-bike vs advanced garage
- Birden fazla motosikleti basic ayri tutmanin minimum davranisi nedir?
- Advanced multi-bike/garage value hangi ek ihtiyaclarda baslar?
- Premium multi-bike capability core motorcycle separation/reminder/history'yi nasil bozmamali?

### Q162-Q165 — Transfer disagreement and repeated transfers
- Former owner correction proposal current owner tarafindan reddedilirse iki iddia nasil gorunmeli?
- Disputed historical claim ne zaman/kim tarafindan eklendigiyle nasil anlasilir kalmali?
- Motosiklet ikinci/ucuncu kez el degistirirse previous partial histories/provenance nasil algilanmali?
- Later owner complete history iddiasi ile previous partial disclosures arasinda nasil trust expectation olmali?

### Q166-Q168 — Withdrawn contribution downstream effects
- Withdrawn community evidence official guide/claim'de kullanildiysa ne olmali?
- Previously exposed/affected users'a hangi durumda correction/re-review bilgisi verilmesini beklersin?
- Contribution geri cekildi diye official guide otomatik invalid mi olmali, yoksa hangi kanita gore yeniden degerlendirilmeli?

### Q169-Q171 — Shared/collaborative deletion ownership
- Owner motorcycle record'u silmek isterken collaborator'in kendi contribution/evidence'i varsa hangi ownership expectation vardir?
- Contributor kendi ekledigi bir kaydi geri cekmek/silmek isterse shared history trust nasil korunmali?
- Owner access'i kaldirdiginda old attributed records'in history'de kalmasi/ayrilmasi konusunda beklenti nedir?

### Q172-Q174 — Evidence explanation depth by risk
- Hangi low-risk context'te short evidence label yeterli olabilir?
- Hangi high-risk/high-trust context'te explicit `what/evidence/reviewer/unverified` explanation zorunlu olmali?
- Trust details cok fazla bilgi kalabaligi yaratirsa user hangi bilgiyi first-level, hangisini optional detail olarak gormek ister?

### Q175-Q177 — Local data -> profile transition
- Account-light use sonrasi profile acarken existing local records'in kaybolmamasi icin hangi product assurance gerekir?
- User profile olusturmak istemezse local value'nin hangi kismi devam etmeli / hangi kalici value natural olarak profile gerektirebilir?
- Profile transition'da duplicate/conflicting motorcycle/history ortaya cikarsa user ne bekler? Teknik merge algorithm sorma.

### Q178-Q180 — Mid-repair guide materially changed after re-check
- Online re-check sonrasi current guide eski guide'dan kritik bicimde farkliysa user first neyi bilmek ister?
- Motorcycle fiziksel olarak old guide'in orta adimindaysa yeni guide'a gecis nasil guven vermeli?
- New guide mevcut physical state'i guvenle map edemiyorsa application/teaching/professional option nasil ayrilmali?

### Q181-Q183 — Active repair interruption/re-entry
- Telefon/app kapanir veya attention kesilirse geri donuste hangi context korunmali?
- Critical step yarim kalmis olabilirken resume oncesi hangi confirmation/check beklenir?
- User nerede kaldigindan emin degilse product nasil ilerlememeli ve nasil recovery sunmali?

### Q184-Q185 — Paid-service evidence dispute
- Service document `islem yapildi` derken owner observation bununla celisirse iki claim nasil temsil edilmeli?
- Paid service record'un evidence/dispute durumu maintenance schedule veya future decisions'i etkilerken product hangi uncertainty'yi gostermeli?
