## MEVCUT GUVENILIR BAGLAM — TEKRAR SORMA

- Core priority kendi motosikletinde islem yapan beginner ve experienced owner'dir; basic record tracking de first-product value'dur.
- Basic history core'da motorcycle, work, date/km, actor, outcome, important safety notes, evidence level ve correction continuity'yi korur; old basic history storage pressure nedeniyle silinmez.
- Basic multi-bike isolation core'dur: each motorcycle history/km/reminder/active-work state independent kalir. Advanced garage cross-bike analysis, bulk planning, richer collaboration ve large-archive search gibi ek degerde baslar.
- Professional/service initial direct target degildir; owner-invited contributor olabilir. Role automatic verified status yaratmaz.
- Readiness stop'ta assessment error check -> self-remediation -> evidence-based re-validation vardir. Professional recommendation optional support; unverified critical condition mandatory application gate'tir.
- Teaching content ile current-motorcycle application instruction ayridir.
- Evidence vocabulary common logic tasir fakat verified claim context-specific'tir. Low-risk routine content short label ile baslayabilir; high-risk/disputed context claim + motorcycle + evidence + reviewer + uncertainty aciklar.
- Selective/repeated ownership transfer partial-history semantics tasir; owner/period/coverage/gaps gorunur. Rejected correction silent overwrite yapmaz; accepted record ve disputed proposal ayri kalabilir.
- Community evidence withdrawal dependent official guide/claim icin re-review tetikler. Independent evidence yeterliyse claim kalabilir; yetersizse verification/application korunamaz.
- Owner delete baska contributor'in independent evidence'ini sessizce silemez. Contributor own evidence'i geri cekebilir; linked history'de withdrawal trace kalir ve trust yeniden degerlendirilir.
- Account-light -> profile transition scope preview, no-silent-loss ve conflict review gerektirir. Silent overwrite yoktur. Profile olmadan guide/local history/interrupted-work value devam edebilir.
- Material guide change mid-repair change/safety/stop impact'ini aciklar; current physical state new guide'a remap edilmeden continuation olmaz.
- Active-repair interruption resume, last viewed step'e donmek degildir; last known safe state + current physical/safety revalidation gerekir.
- Paid-service document ile owner evidence conflict'i unresolved ise maintenance counter/future guide decisions verified completion gibi ilerleyemez.
- Final technology, data model, legal interpretation, UI component, storage quota, price veya architecture bu phase'de secilmez.

## BU TURDA MUTLAKA DERINLESTIRILECEK 10 ALAN

1. **Contributor evidence withdrawal vs independent/transferred copies**
   - Contributor own evidence'i geri cektiginde evidence baska owner'a transfer edilmis/independent copy olmuşsa product-level relationship ne olmali?
   - Withdrawal source-copy'i mi, provenance/trust state'i mi, public visibility'yi mi etkiler?
   - Legal ownership veya database replication architecture sorma.

2. **Disputed claim resolution with new independent evidence**
   - Accepted/disputed service/history claim'e sonradan yeni bagimsiz evidence gelirse hangi product outcome beklenir?
   - Dispute ne zaman resolved/superseded sayilabilir; eski disagreement history'de nasil korunur?

3. **Minimum historical-claim states**
   - User acisindan accepted/disputed/evidence-withdrawn/unknown/resolved/superseded gibi hangi ayrimlar gerekli?
   - Gereksiz state taxonomy uretme; gercek user meaning'i kesfet.

4. **Material guide change — previously performed physical action recovery**
   - Old guide ile yapilan bir sokme/ayar/baglanti new guide'da artik onerilmiyorsa user ne bekler?
   - Reversal, inspection, evidence capture veya external support beklentisini product-level kesfet.

5. **Long interruption — saved context vs current physical reality**
   - Hours/days later resume durumunda hangi previous state yeniden verify edilmeli?
   - Environment, motorcycle movement, someone else touching bike, temperature/energy, missing parts gibi product-level expectations'i kesfet.

6. **Profile migration cancel/failure/rollback**
   - User migration'i yarida iptal eder veya process fails olursa local records/new profile records hakkinda ne bekler?
   - Technical transaction/sync algorithm sorma.

7. **Affected-user boundary after withdrawn evidence/correction**
   - Guide'i sadece gorup cikmis user, relevant step'i acmis user, step'i applied user, completion record'u olan user arasinda correction reach-back expectation nasil degisir?
   - Exact notification channel/SLA secme.

8. **Evidence detail: beginner vs experienced**
   - Beginner/experienced user trust detail'i nasil farkli sunulabilir?
   - High-risk explicitness speed ugruna azaltilabilir mi, hangi kisimlar invariant?
   - Final UI layout/component sorma.

9. **Core invited collaboration vs premium extensive collaboration**
   - Basic shared-bike collaboration free core'da minimum neyi korumali?
   - Premium collaboration hangi scale/coordination/analytics value'da baslamali?
   - Exact pricing/tier/user limits isteme.

10. **Advanced garage vs basic shared trust boundary**
   - Bulk planning, cross-bike analysis, archive search ve richer permissions'in hangileri advanced value?
   - Attribution, revoke, private-content isolation ve historical integrity gibi trust basics premium'a baglanabilir mi?
